## 同一カード・購入リンク

- 同じゲームカードの表示上の同一性は `baseCardId` で判定する。
- R、P、P＋、ARなどの物理バージョンの元データは統合・削除しない。
- 「同一カードをまとめる」ONでは `baseCardId` ごとに1種類として表示し、OFFでは物理バージョンごとに表示する。
- Card Laboで検証済みの個別購入リンクは767件を維持する。
- 購入リンクは物理バージョン単位で保持し、別バージョンのURLを流用・統合しない。
- まとめ表示では、存在する検証済み購入リンクをカード表面に表示する。
- 「バージョンを見る」内では購入リンクを重複表示しない。ただし各物理バージョンの公式カード情報リンク、レアリティ、収録商品、所持操作は維持する。

## 検索・フィルター・表示

- フリーワード検索は、半角／全角空白で分けた複数語のAND検索。各語はカードの既存検索対象全体から判定する。
- グループ、カード種類、メンバー、COST／SCORE、収録商品、所持状態、候補のみ、ソートは既存の組み合わせ条件を維持する。
- メンバー複数選択は同一フィルター内OR、他フィルターとはAND。
- 学年／ユニットはメンバー候補の表示分類であり、選択状態・絞り込み条件を変えない。
- カード種類とグループの最後の選択は、それぞれ専用のlocalStorage keyで安全に復元する。不正値は `すべて` へ戻す。

## 所持・候補・デッキ

- 所持枚数は物理バージョン単位で0～99枚。0枚は保存しない。
- まとめ表示での所持数とデッキ用途の所持数は、同じ `baseCardId` の物理バージョンを合算する。
- 候補は全デッキ共通のブックマークであり、デッキ切替・複製・削除で失わない。
- デッキは複数保存でき、編集対象はアクティブデッキのみ。
- 同一ゲームカードの採用上限は4枚。
- 完成形はメンバー48枚、ライブ12枚、合計60枚。未完成時は残り枠を計算する。
- デッキ一括消去、JSON／クラウド読み込み、クラウド履歴復元は、既存の1回限りのUndoを維持する。
- レシピコピーとAI相談コピーはアクティブデッキだけを対象にする。AI相談の候補選択は一時的で、候補そのものを変更しない。

## JSONデータ移行

- export/importはversion 3を現在形式として維持し、version 1／2／3の読み込み互換を保つ。
- インポートは検証後の完全置換であり、不正データを一部だけ適用しない。
- 旧versionを読み込むと所持情報が存在しないことを明示する。
- JSON移行機能本体・テストは残すが、通常画面には入口を表示しない。

## クラウド同期

- 同期対象は、全デッキ、デッキ名・内容、アクティブデッキ、候補、所持カード。
- 検索語、カード種類、グループ、並び順、表示設定などの端末UI設定は同期しない。
- 同期コードは端末localStorageにのみ保存し、export/importデータへ含めない。
- 保存は手動操作のみ。自動保存、自動同期、定期通信は行わない。
- `revision` による409競合防止を維持し、古い端末が無言でクラウドを上書きしない。
- クラウド最新版とは別に、保存前の状態を直前5世代まで保持する。
- 履歴復元は過去のrevisionへ戻さず、新しいrevisionとして保存する。復元直前の最新版も履歴に残す。
- 未保存表示はdirtyフラグではなく、同期対象version 3 payloadの安定したfingerprintと、最後に正常同期したbaselineの比較で判定する。
- 同期解除はこの端末の同期コード・同期metadata・baselineだけを消し、クラウド・デッキ・候補・所持は消さない。

## 表記と安全性

- リポジトリのテキストファイルは厳密なUTF-8であり、JSONはparse可能でなければならない。
- 基本ハート、ブレードハート、必要ハート、効果文内のアイコンは公式の色・種類・個数を保つ。
- `heart03` のような内部トークンや、色を失ったハート表記を画面に残さない。
- 変更後は `npm run check` を実行する。画面・実機の確認が必要な変更は `docs/MANUAL_REGRESSION_CHECKLIST.md` も実施する。
